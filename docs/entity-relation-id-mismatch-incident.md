# 사고 기록: 1화/2화 엄마-진성 관계 누락 (2026-07)

- **기기/날짜**: SM-S928N, 2026-07-03
- **관련 코드**: `IngestService.generateResult`(소프트 실패 재시도 + 드롭 지점), `IngestService.shadowMatchDescription`(섀도 매칭), `PartialDropRecorder`(신설), `IngestParser`(신규 수리 패스), `IngestSchema`(`PROMPT_VERSION` v2→v3→v4, id 일관성 규칙 추가 후 철회)
- **관련 테스트**: `IngestServiceTest`(소프트 실패 재시도 3건, 섀도 매칭 5건 + 통합 1건, 드롭 기록 1건), `IngestParserTest`(신규 수리 패스 회귀 픽스처), `IdMismatchRateSmokeTest`(androidTest, 관측용 — `IdConsistencyPromptSmokeTest`의 후신)

## 증상

같은 원고(1화 저장 직후 사고 재현을 위해 의도적으로 그대로 재저장한 2화)를 두 번 인제스트했는데, 1화 결과의 그래프에는 "엄마"가 아무와도 연결되지 않은 고아(orphan)로 남았고, 2화 결과에는 "진성-엄마" 관계가 정상적으로 생겼다. 인제스트 자체는 두 번 다 "성공"으로 표시됐다.

## 처음 세운 가설 (틀림)

"2화 프롬프트에는 1화에서 만든 `existingEntities`(엄마 포함)가 컨텍스트로 들어갔고, 1화 프롬프트에는 그게 없었으니 — 세계관 설정집(누적 위키)을 프롬프트에 넘겨주는 효과로 모델이 관계를 더 잘 잡아냈다"는 가설을 처음에 세웠다. **이는 틀렸다.**

## 실제 원인 (정정)

로그(`IngestParser`의 `parse() repaired JSON:` 라인)에서 1화 attempt 2(성공한 시도)가 실제로 뽑아낸 원본을 확인한 결과:

- `entities`에는 `"진성"`이라는 id로 정의돼 있었다.
- `relations`의 앞쪽 항목들은 `"진성"`을 정확히 참조했지만, **뒤쪽 두 개(엄마 관련, 지민 관련)에서만 `"성"`으로 축약**해서 참조했다 — `{"from": "성", "to": "엄마"}`.
- `"성"`은 이 응답의 `entities` 어디에도 정의되지 않은 id라서, `IngestService.ingest`의 `knownIds` 필터(존재하지 않는 id를 가리키는 관계를 제거하는 로직)가 이 관계를 조용히 버렸다.
- 2화 attempt 2(성공한 시도)는 같은 관계를 `"진성"`으로 정확히 참조했고, 그래서 정상 병합됐다.

즉 원인은 **existingEntities의 유무가 아니라, 모델이 같은 응답 안에서 엔티티에 정의한 id를 relations에서 줄여 쓰는 것(entities-relations id 불일치)**이었다. existingEntities는 이 사고와 무관하다 — 우연히 1화(existingEntities 없음)에서 불일치가 나고 2화(existingEntities 있음)에서는 안 났을 뿐, 인과관계가 아니라 상관관계였다.

## 조치

1. **드러내기 (`IngestService.ingest` + `PartialDropRecorder`)**: 같은 응답의 `entities`에 없는 id를 참조하는 관계는 여전히 조용히 드롭되지만, 이제 `ingestLogger.w`로 경고 로그를 남기고 `PartialDropRecorder`(`IngestFailureRecorder`와 같은 패턴, 별도의 `partial-drops/` 디렉터리)로 기기에 기록을 남긴다. 인제스트 성공/실패 판정 자체는 바뀌지 않는다 — 나머지 엔티티/관계는 정상이므로 여전히 성공이다. 느슨한 id 복구(부분 문자열 매칭 등)는 오탐 위험 때문에 이번엔 하지 않았다.
2. **파서 수리 패스 추가 (`IngestParser`)**: 이번 사고를 조사하며 함께 발견한, 현재 수리 정규식이 못 잡던 두 가지 JSON 문법 패턴을 새 패스로 추가했다 — 콤마 뒤 키 이름의 여는 따옴표 누락(`,name":`)과 콜론 뒤 값의 여는 따옴표 누락(`:지민"`). `"엄마마"`(글자 중복) 패턴은 확인 결과 JSON 문법 문제가 아니라 유효한 문자열이 그냥 틀린 id를 가리키는 경우라 — 이건 파서가 아니라 위 1번(`PartialDropRecorder`)이 잡는 부류다.
3. **프롬프트에 id 일관성 지시 추가 (`IngestSchema`, 실험적)**: `PROMPT_VERSION` v3에 "entities에서 정한 id는 relations에서도 정확히 동일한 문자열로만 참조하라"는 규칙을 추가해 원인 자체를 프롬프트 단에서 줄여보려 시도했다. `IdConsistencyPromptSmokeTest`(androidTest, 관측용 — 회귀 게이트 아님)가 실제 1화 원고로 v2/v3 프롬프트 각각 5회씩 생성해 불일치 빈도 변화를 로그로 남긴다.

## 교훈

"성공으로 표시됐다"는 사실이 "관계가 전부 유지됐다"는 뜻은 아니었다 — `IngestService.ingest()`가 파싱 실패(rule 5, 이전 사고)를 넘어 **부분 드롭**도 조용히 삼킬 수 있다는 게 이번에 새로 드러난 지점이다. 원인 조사 시 첫 가설(existingEntities 효과)에 만족하지 않고 실제 로그 원본을 직접 대조한 것이 정정으로 이어졌다 — 그럴듯한 설명과 실제 데이터가 다를 수 있다는 걸 로그로 증명한 사례.

## `IdConsistencyPromptSmokeTest` 관측 결과 (2026-07-03, SM-S928N)

실제 1화 원고로 v2(지시 없음)/v3(id 일관성 지시 추가) 프롬프트를 각각 5회씩 생성(공통 topK=40/topP=0.9/temperature=0.1, 실행마다 다른 seed)한 결과:

| 변형 | 불일치(mismatch) 발생 |
|---|---|
| before (v2, 지시 없음) | 2/5 |
| after (v3, id 일관성 지시 추가) | **4/5** |

**결론: 이번 관측에서는 프롬프트 지시가 불일치 빈도를 줄이지 못했다 — 오히려 늘었다(2/5 → 4/5).** 실행 로그를 보면 v3에서도 "진성"이 관계에서 "성"으로 축약되는, 원래 사고와 정확히 같은 패턴이 재발했고("율->성", "성->핸드폰" 등), 그 외에도 "엄마"가 "엄마음"/"엄음음" 같은 변형으로 갈라지는 패턴이 v2/v3 양쪽 모두에서 반복적으로 나타났다. 표본이 5회로 작아 노이즈일 가능성을 배제할 수 없지만, 적어도 이 한 줄짜리 프롬프트 지시만으로 문제가 해소된다는 근거는 이번 관측에서 나오지 않았다 — "실험적" 조치라는 표기 그대로 유효하다. 후속 조사가 필요하면 표본을 늘리거나(더 많은 seed), few-shot 예시를 relations에도 추가하는 방향을 검토할 것.

부수적으로, 이번 관측 중 기존에 알려지지 않았던 별도의 JSON 문법 실패 패턴도 확인됐다(`"id": "율",` 다음 줄에 홀로 `,`만 있는 고아 콤마) — v2 run 1/2가 이 패턴으로 파싱 자체에 실패했다. 이번 배치의 스코프 밖이라 별도 조사가 필요하다.

## 후속 조치 (2026-07, 관측 결과에 따른 대응)

위 관측(v2 2/5, v3 4/5 — 프롬프트 지시가 효과 없음)에 따라 다음을 진행했다:

1. **`IngestSchema`의 id 일관성 지시 철회.** `PROMPT_VERSION`을 v3에서 v4로 올렸다 (v3 번호는 재사용하지 않음 — 위 측정 기록이 실제로 존재했던 v3 프롬프트를 가리키고 있어서, v2로 되돌리며 번호까지 v2로 되돌리면 그 사실이 사라진다). v4의 프롬프트 텍스트는 규칙 한 줄만 빼면 v2와 바이트 단위로 동일하다.
2. **`IngestService.generateResult`에 소프트 실패 재시도 채택.** 파싱은 성공했지만 relations가 이번 응답의 entities에 없는 id를 참조하는 경우, 마지막 시도가 아니라면 그 시도 전체를 버리고 다음 attempt로 넘어간다(파싱 실패와 같은 attempt 예산 공유, 새 예산 추가 없음). 마지막 시도에서는 기존처럼 수용 + 기록.
3. **`IngestService.shadowMatchDescription` 채택(섀도 모드).** 미해결 id에 대해 "부분 문자열 포함 관계이고 후보가 정확히 1개"인 경우만 매칭으로 보고 `PartialDropRecorder` 기록에 함께 남긴다. 병합에는 적용하지 않는다 — 드롭은 그대로 일어난다.
4. **`IdConsistencyPromptSmokeTest` → `IdMismatchRateSmokeTest`로 교체.** v2/v3 비교라는 원래 목적이 끝났으므로, 같은 골든 픽스처(실제 1화 원고)를 재사용해 이제는 "위 1·2번 완화책을 거치고도 남는 잔존 불일치율"과 "그 잔존 불일치에 대해 섀도 매칭이 후보 1개를 찾아내는 비율"을 관측하는 테스트로 바꿨다. 후자의 수치가 충분히 높게 나오면 섀도 매칭을 실제 병합 복구로 승격하는 근거가 된다.

원인(모델이 같은 응답 안에서 id를 줄여 쓰는 것) 자체는 해결된 게 아니다 — 프롬프트로 원인을 줄이는 시도는 효과가 없었다는 게 이번에 확인된 사실이고, 그래서 대응 축을 "생성 전 예방"에서 "생성 후 탐지/재시도"로 옮긴 것이 이번 후속 조치의 핵심이다.
